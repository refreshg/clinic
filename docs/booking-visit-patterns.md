# ვიზიტის მართვის 6 პატერნი (booking / visit patterns)

წყარო: `docs/ჯავშანივიზიტი - 12.07.26.docx` (სტომატოლოგიური კლინიკის ვიზიტის მართვის
სტრუქტურა). ეს პატერნები Phase 3-ის (ჯავშნის ციკლი) დიზაინის საფუძველია — თითო პატერნს
ერთვის **როგორ ვახორციელებთ Odoo 19-ში** (მაქსიმალურად სტანდარტის reuse-ით).

---

## 1. სტატუსების მართული ლაივ-ციკლი (State Machine)
**რას ამბობს რისერჩი:** ჯავშნის სტატუსები მკაცრად განსაზღვრული და ავტომატიზირებულია:
`მოთხოვნილი → დაჯავშნილი → დადასტურებული → მოსული → პროცესში → დასრულებული → გადახდილი`
(+ `ხელახლა დაჯავშნილი`, `გაუქმებული`, `გაცდენა/No-Show`). თითო სტატუსს აქვს ტრიგერი/
ავტომატიზაცია და ფერის ცვლილება; No-Show ავტომატურად, თუ დრო გავიდა და პაციენტი არ მოვიდა.
**Odoo-ში:** `state` Selection + `widget="statusbar"` + header workflow-ღილაკები (action
მეთოდები); ფერი kanban/calendar-ში; No-Show — scheduled action (cron). გაუქმებაზე მიზეზი
სავალდებულო; ხელახლა-დაჯავშნა ინახავს ძველი დროის ისტორიას.

## 2. სავალდებულო კარიბჭეები / წინაპირობის guard-ები (Mandatory Gates)
**რას ამბობს რისერჩი:** გადასვლა იბლოკება, სანამ პირობა არ სრულდება:
- „პროცესში" აკრძალულია რთულ პროცედურაზე, თუ **ინფორმირებული თანხმობა** არ არის ხელმოწერილი;
- ადმინი ვერ ხურავს ბარათს, სანამ **შემდეგი ნაბიჯი** არ მიეთითება (შემდეგი ვიზიტი / რექოლი /
  მკურნალობა დასრულებულია);
- ექიმი ვერ ასრულებს ვიზიტს, სანამ **პირველადი მონაცემები** (კბილის ნომერი, დიაგნოზი) არ შეავსო.
**Odoo-ში:** transition-მეთოდებში guard (`raise UserError`), `@api.constrains`, state-ზე
დამოკიდებული required ველები. „გამტარ" ლოგიკას ვწერთ მოდელში, არა view-ში.

## 3. ეტაპობრივი დროის აღრიცხვა (Stage Time Tracking)
**რას ამბობს რისერჩი:** დროის ტაიმერები მიბმულია სტატუსებზე — **მოცდის დრო** (Check-In →
პროცესში), **სავარძლის/ვიზიტის დრო / Chair Time** (პროცესში → დასრულებული), **ბუფერული დრო**
(დასუფთავება/მომზადება ვიზიტებს შორის, ავტომატურად კალენდარში).
**Odoo-ში:** stored datetime ველები transition-ებზე (`checkin_time`, `start_time`,
`end_time`) + computed ხანგრძლივობები (waiting/chair); ბუფერი — appointment type-ის default
duration-ში; ხანგრძლივობა პროცედურის ტიპიდან ავტო, რედაქტირებადი.

## 4. მოვლენაზე-დაფუძნებული შეტყობინებები და შეხსენებები (Event-Driven Notifications)
**რას ამბობს რისერჩი:** Check-In-ზე ექიმს/ასისტენტს მიდის **ხმოვანი + ვიზუალური** შეტყობინება
(„პაციენტი მოვიდა"); რიმაინდერები: 24სთ ადრე SMS, 20სთ ადრე ზარი/WhatsApp — თითოს აქვს
**delivery/დადასტურების სტატუსი** (გაგზავნილი/მიღებული/ვერ გაიგზავნა/დადასტურებული…); No-Show-ზე
ავტო-შეტყობინება პაციენტს პოლიტიკის ახსნით.
**Odoo-ში:** `bus.bus._sendone` (ლაივ push) + custom OWL service (toast + ხმა); `mail.activity`
(to-do ექიმზე); `sms` + `mail`; scheduled action (cron) რიმაინდერებზე; delivery-status ველები.

## 5. გეგმა → ფაქტი → ინვოისი შეჯერება (Plan-to-Actual Reconciliation)
**რას ამბობს რისერჩი:** მკურნალობის გეგმის პროცედურები (ფასთწარმოქმნა + დროის კალკულაცია)
დინამიურად უკავშირდება ვიზიტს; ექიმი ვიზიტზე ნიშნავს **ფაქტობრივად ჩატარებულ** პროცედურებს
(შეიძლება გეგმისგან განსხვავდებოდეს); დასრულებაზე **ავტომატურად გენერირდება ინვოისი** ჩატარებულიდან;
გეგმა vs ფაქტი **სხვაობა ჩანს**; ფასის ცვლილება ავტომატურად ეცნობება მენეჯერს/მთავარ ექიმს.
**Odoo-ში:** appointment-ის procedure lines ↔ `clinic.procedure.history` ↔ `account.move`
(auto-invoice ჩატარებულიდან); computed deviation (planned vs actual); `tracking=True` +
activity ფასის ცვლილებაზე; კავშირი `treatment_plan_status`-თან.

## 6. თანხმობის და უსაფრთხოების ფენა (Consent & Safety Compliance)
**რას ამბობს რისერჩი:** **კრიტიკული სამედიცინო შეხსენება წითლად** (ალერგია ანესთეტიკზე,
ორსულობა, ჰეპატიტი…); თითო პროცედურაზე **ინფორმირებული თანხმობა** (ციფრული ხელმოწერა/ატვირთვა/
SMS) — სავალდებულო დაწყებამდე; პერსონალურ მონაცემებზე / EHR-ზე / ფოტო-ვიდეოზე თანხმობა;
**მშობლის თანხმობა** არასრულწლოვანზე / შშმ პირზე.
**Odoo-ში:** `clinic.patient.document` (consent + `signature` widget — უკვე Rev-A-შია);
კრიტიკული alert `decoration-danger` / `<div class="alert alert-danger">`; guard (#2) — თანხმობის
გარეშე „პროცესში" აკრძალვა; `guardian_id` (Rev-A) არასრულწლოვანზე.

---

### გამჭოლი პრინციპი
ეს 6 პატერნი ერთმანეთს კრავს: **State Machine** (1) ატარებს ვიზიტს ეტაპებზე; **Guards** (2)
იცავს მონაცემთა/იურიდიულ მთლიანობას; **Time Tracking** (3) ზომავს ეფექტიანობას; **Notifications**
(4) კრავს პაციენტს↔ადმინს↔ექიმს; **Plan→Actual→Invoice** (5) კრავს კლინიკურ ნაწილს ფინანსებთან;
**Consent/Safety** (6) — იურიდიული დაცვის ფენა. ყველა აგებულია Odoo-ს სტანდარტულ ძრავებზე
(`state`/statusbar, `mail`/`bus`, `account`, `calendar`).
